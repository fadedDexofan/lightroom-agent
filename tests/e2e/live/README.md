# Live-test kit

Reproducible fixtures and helpers for live testing the plugin against a real Lightroom Classic (macOS only, LrC 15.6 and 16.0). The mask tools need a live Lightroom, so CI cannot cover them. This kit makes a live run repeatable: the same images, the same throwaway catalog setup, the same pixel checks.

Everything that needs no Lightroom (PNG/EXIF encoders, orientation maths, manifest verification, catalog guard, preview maths) has unit tests in `unit/`. CI runs them (`mise run live:test`).

## Safety rules

- Live tests run only in a throwaway catalog. `lib/catalog-guard.mjs` finds the open catalog from Lightroom's open files (`lsof`) and refuses unless its folder holds `lrmcp-live-catalog.json` (written by `setup-catalog.mjs`) or `LRMCP_LIVE_THROWAWAY_CATALOG` names it. The real catalog (`~/Pictures/Lightroom`) is always refused, marker or not.
- `setup-catalog.mjs` clicks File > New Catalog while the real catalog is open, and does nothing else to it. It writes no marker and imports nothing until the new catalog is open and verified.
- The throwaway catalog is rebuilt, never committed. Never commit a `.lrcat`, a photo of unknown license, or a depth HEIC.
- Check the frontmost process before every click or keystroke. `ensureLightroomFrontmost()` activates Lightroom and throws if it still is not in front. Edge, Discord, ghostty and sail steal focus.
- Drive dialogs with Accessibility (AX) only. Do not send keystrokes into a window you have not confirmed. Do not force quit Lightroom or remove another process's socket.
- Back up the installed bundle outside `$TMPDIR` (macOS wipes it), restore it afterwards, verify with `diff -rq`.
- End the session on the real catalog in the Library module, ports 58763/58764 listening, Plug-in Manager closed, and `node tests/e2e/mcp-runner.mjs tool list_collections '{"limit":1}'` answering.

## Bootstrap

```sh
mise run build
mise run live:fixtures
node tests/e2e/live/install-bundle.mjs install
mise run live:setup
node tests/e2e/live/smoke.mjs
```

- `live:fixtures` generates the synthetic images, downloads the CC0 raw samples, verifies hashes and verifies the generated files. Output goes to `tests/e2e/live/.fixtures/` (gitignored). Set `LRMCP_LIVE_FIXTURES_DIR` to share one folder between worktrees.
- `install-bundle.mjs install [candidate-dir]` backs up the installed bundle to `~/.cache/lightroom-mcp-live-backups/<stamp>/`, installs the candidate (default: this checkout's plugin), and verifies with `diff -rq`. It lists added Lua files: Reload Plug-in does not see them, so quit and reopen Lightroom. The File > New Catalog relaunch in the next step also loads the new files.
- `live:setup` (`setup-catalog.mjs`) needs Lightroom running and the Accessibility permission for the process running `osascript`. It creates `~/Documents/lrmcp-live-<stamp>/` through File > New Catalog, waits for the relaunch, dismisses the blocking modals, waits for the plug-in, copies the fixtures into `<catalog folder>/images/`, imports each through `import_photos`, and writes photo ids by fixture name into `<catalog folder>/lrmcp-live-catalog.json`. Options: `--name`, `--parent-dir` (must be the folder the dialog proposes, normally Documents).
- `smoke.mjs` proves the kit works: EXIF orientation of all 8 previews, `list_masks`, a linear gradient on `orient_6` (preview diff by region), a radial gradient on `wide_plain` (IoU against the analytic ellipse), and the stored develop row. It removes its masks.
- `reopen-catalog.mjs <path to .lrcat>` quits Lightroom (accepting "Do you really want to quit?") and opens it with that catalog file, then reads the open catalog from the main window title. Lightroom 16.0 sometimes ignores the file it was launched with and opens its most recent catalog instead; the script then quits and launches it again with the file, up to three launches within the time limit, and prints how many it took. On Lightroom 16.0 File > Open Recent has no Accessibility name, so the menu route does not work. To restore the bundle, run `install-bundle.mjs restore` while Lightroom is closed, before reopening.

Fixtures added to the generator after a catalog was set up: run `mise run live:fixtures`, then `node tests/e2e/live/setup-catalog.mjs --add-missing` with the throwaway catalog open. It imports only the fixtures the marker does not list yet and adds their ids to it.

Manual fallback: if the New Catalog dialog proposes another folder or AX fails, create an empty catalog by hand (File > New Catalog in an empty folder), leave it open, and run `node tests/e2e/live/setup-catalog.mjs --adopt-open-catalog`. It refuses the real catalog and any catalog that already holds photos.

## Certifying mask writes

`node tests/e2e/live/certify-mask-writes.mjs` makes mask geometry writable outside the throwaway catalog after a Lightroom update. It refuses unless the open catalog carries the kit marker (the plug-in admits guarded writes there without a certification), resets the develop settings of `wide_plain`, `ramp256`, `chart80`, `orient_1`, `pano`, `arw_14bit`, `arw_12bit` and, when the catalog has one, `depth_heic`, and runs every guarded tool once: linear and radial gradient create and update, brush with an erase stroke, luminance range, a single-sample colour range on `chart80` with the l, a, b Lightroom itself sampled from its red patch (never two samples), a depth range (nearest 0 to 0.3, Exposure −1) on `depth_heic` when the catalog has one, which must darken the near table front and leave the far background unchanged, copy of develop settings with masks, a guarded write next to a Lightroom-authored sky mask (its raw entry and rendered effect must stay the same), Landscape, People on a photo without a person (refusal and cleanup), a sky batch, and one linear gradient on `pano` per family of local sliders in the server's `LOCAL_KEYS` table (sliders whose stored fields differ only by the colour-grading wheel are one family; any other stored field name or stored scale is its own), each with a single slider halfway from its neutral to its top; the creation tool confirms the slider through Lightroom's own reading, and the step compares the new mask's raw stored field with the written value divided by the table's scale, within the table's tolerance, and names the key, the written, the expected and the stored value when they differ. Then `set_mask_adjustments` sets every key of the table on the first of those gradients, a quarter of the way from neutral to the top, so Lightroom stores the fields itself; the step compares each stored field with value / scale within tolerance, so the table's scales are checked against Lightroom independently of the plug-in's writer. A field Lightroom does not store on a linear gradient, or a slider the call left unchanged, goes into the record's not-exercised list instead of failing. Each step reads the raw `MaskGroupBasedCorrections` before and after through `get_develop_settings` and the pinned-format check of the resulting masks through `get_mask_write_admission`; the steps that create a visible effect also compare previews. Only when every step passed does it write `~/.config/lightroom-mcp/mask-certification.json` (the path the plug-in reports) with the Lightroom version and build as the plug-in reads them, the process versions exercised, the checks, the checks with a rendered comparison, what was not exercised (depth range without a supplied depth photo, or when Lightroom found no depth map in it, which is then not a failure) and the kit commit; a failed or interrupted run leaves the previous record. The same run checks the range tables separately: `describe_develop_keys` on `arw_12bit` gives Lightroom's range for every number key of `DEVELOP_KEYS`, and on `pano` with the first family gradient selected (`mask_id`) for every local slider of `LOCAL_KEYS`; the run takes the tool's own verdict (`differs`, within its tolerance) instead of comparing again. The record's `ranges` names the build, the static keys compared, `stale_ranges` (key, table range, Lightroom's range) and the keys not compared (photo-dependent ranges, or no range reported) with their live range. Ranges never decide mask admission; a stale static range is written into the record and the run file, named in the last lines, and makes the command exit non-zero, so the table must be corrected before the build is installed. It leaves the masks on those fixtures and a run report in `<catalog folder>/certification-runs/`; it exports nothing. `get_mask_write_admission` shows the result on any catalog.

## Verification matrix

For rating and flag changes, use `set_rating_and_flag` with `photo_ids` and either field or both. On a disposable copy, set `rating: 3` and `flag: "pick"`, read back `rating` and `flag` with `get_photo_metadata`, then restore both original values. Rating `0` and flag `"none"` clear their fields; an omitted field stays unchanged.

For `get_photo_preview.region`, compare one `chart80` patch with the same pixels
from a full-frame preview at the source size reported by `requested_size`.
Require mean RGB differences within 0.03 per channel and a flat patch interior.
On `orient_6`, crop a displayed corner and compare with
`expectedDisplayedCorners(6)`. Record full-frame, small-preview and region
dimensions and image-token estimates: a region requests a larger source before
cropping, capped at size 2048. Verify omitted-region bytes and metadata retain
their full-frame behavior, and malformed regions fail before rendering.

`node tests/e2e/live/duplicate-groups.mjs` reads the two ARW fixtures and `wide_plain`, derives the raw capture gap from `find_duplicate_groups.photos`, and checks that only the ARWs group at that gap. It verifies ratings, flags, keyword paths and reported collections stay unchanged. `get_photo_metadata.date_time_original` remains a display string and is never parsed. The script reads the marked throwaway catalog without changing its shared fixtures.

`node tests/e2e/live/photo-stats.mjs` checks `get_photo_stats` on untouched `ramp256` and `wide_plain`: each ramp quarter holds 25 percent of the histogram mass within 5 points; plain gray has mean luminance 110 within 4 and no clipping. The script only reads the marked throwaway catalog.

For a catalog whose shared fixtures already have develop edits, import your own gray ramp and gray-110 images and pass their IDs as `node tests/e2e/live/photo-stats.mjs RAMP_ID PLAIN_ID`. Preserve the shared fixtures and their edits.

For AI metadata, run `node tests/e2e/live/ai-metadata.mjs write`, then `verify`
after Reload Plug-in and again after quitting and reopening Lightroom. Run
`clear` to check clearing and restore the fixtures' original plug-in values.
Each phase checks that keywords, title and caption stay unchanged. The new
metadata provider registers a persistent schema: obtain approval of its field
IDs and types before installing it, keep it confined to the throwaway catalog,
and restore the original bundle while Lightroom is closed before reopening
the real catalog. Finish with `node tests/e2e/live/smoke.mjs` on the throwaway
catalog.

Positions are always in the frame of the rendered preview (after crop, straighten and orientation); Lightroom stores masks in the source frame before all three (`ImageFrame.lua`).

## Catalog removal check

After installing the candidate bundle and restarting into the marked throwaway catalog, run `node tests/e2e/live/remove-from-catalog.mjs`. It imports three uniquely named JPEG copies, verifies confirmation guards, removes two in one call, checks the catalog count and every original fixture, verifies surviving selection, and checks all three files still exist after cleanup. The copied files remain in the throwaway catalog folder for inspection. Run with exclusive app and bridge ownership: the script briefly closes MCP to stage selection through the test-only TCP action.

Stop without retrying if removal opens a blocking dialog, affects only the active photo, or removes unrequested virtual copies or stack members. Check master/virtual-copy and stacked-photo behavior manually on additional disposable imports before accepting a new Lightroom version. The tool refuses a master unless all its virtual copies are explicitly included. It restores module, sources and selection; Library remains in grid view because the documented SDK has no primary-view getter.

## Structural proofs

Each script checks one area on the open throwaway catalog, prints a pass/FAIL line per check with its measurements, and writes the whole report as JSON with `--evidence <file>`; it exits non-zero when any check failed. They restore what they change or work on their own virtual copies.

- `detail-crop.mjs`: on `checkerboard` a whole-frame region at `max_edge` 512 is refused before the render (outcome failed, "nothing was rendered", with the largest region width and height the photo allows) and leaves the develop history and `lastExportTimestamp` as they were; one successful `get_photo_detail` then adds exactly one `Export` develop history step and sets `lastExportTimestamp` (both read from the open catalog 3 s after each reply), and the reply's `render.source` is `export` with `left_on_photo` naming both; that render removes a render folder planted under `lightroom-mcp-detail` with a name started ten minutes earlier (Cocoa-epoch milliseconds, as `LrDate.currentTime` counts) and keeps one started at planting time and an unrelated folder (the folder names Lightroom's own renders use are recorded); its crop alternates pixel by pixel; the suggested width and height, sent back as a region at x 0.3004, y 0.2006 where outward rounding adds a pixel, render within 512; render sizes equal the displayed size and `get_crop`'s size of `checkerboard`, `wide_plain`, `orient_6` and a cropped `wide_plain`; the render size against `get_crop`'s is recorded, not asserted, for `wide_plain` cropped at 8 degrees, a virtual copy of `arw_14bit` with Upright 4 and Vertical −20 (removed afterwards) and `arw_14bit`; on `arw_14bit` the time, the peak size of Lightroom's temporary render folder and the JPEG quality of the written render (copied while it exists; all quantisation tables 1 means quality 100); photo count, selection and develop settings unchanged and no render folder left under Lightroom's temporary `lightroom-mcp-detail` afterwards (each call renders into a folder of its own, which the server removes after reading). Output sharpening is taken from the reply: the written file does not record it.
- `crop-frames.mjs`: `set_crop` at 8 degrees on `markers_1`, `markers_6` and `markers_8`; a radial written at the red disc's position in the cropped preview renders within 0.002 of it; a horizontal linear gradient renders horizontal; with Upright 4 the write warns; a 4:5 `aspect` crop on `orient_1`, `orient_6` and `orient_8` renders at 4:5 within 0.5 % around the centre; with `relative_to: "crop"` a turned aspect fit stays inside the current crop, while a turned rectangle is held only to the photo's edges (accepted at 8 degrees beyond the crop, refused at 40). ## Known traps

`node tests/e2e/live/style-summary.mjs` checks the single-photo median on `arw_14bit`, restores its exposure/rating and all other five-star ratings, then times a 200-photo summary (requires `make-batch.mjs` and `import-batch.mjs` first). Issue 387's prerequisite was checked on LrC 15.6 with a fresh synthetic import: protected raw `isExported` was Boolean `false`, `export_photos` exported one JPEG, and the same raw getter returned Boolean `true`. The diagnostic action was private to the temporary probe bundle. The summary intersects exported state with rating, uses SDK numeric keys, and reports settings omitted by the per-group size limit.

- `LrInitPlugin` runs only when Lightroom's window is first activated: after a relaunch that leaves another app in front, no server starts. `setup-catalog.mjs` and `ensureLightroomFrontmost()` activate it.
- "No X detected" and "Enable address lookup?" modals block the UI and make mask creation silently do nothing. Run `dismissBlockingModals()` after every launch and after any AI mask call that finds nothing.
- `get_photo_preview` is stale right after a photo enters Develop and can answer "error loading thumb" after a settings change until you select another photo and back. Use `measureChange` (stable twice before, 3.5 s wait, stable twice after) or a diff shows a false uniform change.
- The develop-settings sqlite row lags until you switch photos. Lightroom can also show a change in the panel and never save it, so verify through history or the flushed row, never the panel.
- Develop zoom changes between photo opens. Use View > Toggle Zoom View for Fit before pixel work.
- Reload Plug-in does not see an added `.lua` file (restart Lightroom), and when `mise run plugin:reload` reports that it could not close Plug-in Manager, the open window blocks clicks: `closePluginManager()`.
- After switching catalogs the plug-in can bind and then drop its sockets after the 10 s no-client timeout: Plug-in Manager, Stop Server, Start Server.
- `import_photos` silently skips RAF and CR3. ARW, CR2, NEF and JPEG import. Imports take about 1.2 s per small JPEG; pass a long `timeoutMs`.
- A Color Range with two PointModels crashes Lightroom and crash-loops the catalog. If it happens, quit Lightroom normally and `restore` a snapshot.
- Take a snapshot (`catalog-snapshot.mjs snapshot <label>`) before any test that writes masks you cannot delete again.
- klaudiush rejects comments in new code, also in JS. Put the reasoning in names and in this README.

## Remove spots (Lightroom Classic 15.6)

`list_spots`, `update_spot` and `delete_spot` use the documented SDK spot calls. Make two Heal spots manually on an owned virtual copy in the marked catalog. Compare module, source, selection and active tool before and after success and failure, including a call that opens Remove from Loupe. Remove only the owned copy afterwards.

Live SDK probe: `getAllSpots` works with Remove closed. `getSelectedTool` calls Remove `dust`.
