# Lightroom Agent

A broad, verifiable Lightroom Classic API for agents, served by one backend behind an MCP server and a scriptable CLI. Verified capabilities are ported selectively from znznzna/lightroom-cli.

Local, untracked facts about the owner and this machine are in `CLAUDE.local.md` when it exists; read it first.

The aim is a better tool than the existing ones, judged by the quality of the photographs an agent can produce with it and by how much of Lightroom it can drive. Those two outrank token cost and development effort.

## Ownership

This codebase is yours: what it's for and how it's built are your call, and you'll keep building on it.

- The API is pre-release. A tool's shape, name, default or vocabulary stays only while it is the best one for the calling agent; "it was like this before" is not a reason. Update README, GLOSSARY, the ADRs and the bundled skill in the same change as the API.
- Outside your ownership: the user's catalog and photographs, what is installed into their Lightroom and when a live session takes it over, publication (push, release, the MIT license) and the order of work the maintainer has set. These need the maintainer's explicit word.

- `skills/lightroom-agent` is the bundled skill. `npm run build` regenerates the MCP prompt and the mcpb prompt from it; the npm package, the repository-root plugin and `codex/` carry the folder itself. `agents/openai.yaml` is its metadata for Codex.

- The Lightroom tools act on whatever catalog Lightroom has open; do not call them without the user's permission. To run this checkout's server from a client, add it as CONTRIBUTING.md describes.
- For undocumented APIs, distinguish a discovered symbol, a callable signature, a persisted effect and a verified render. Widen a version or format guard only with evidence from that exact Lightroom version.
- Keep one mutating worker; delegate independent read-only investigation. The parent owns integration, final checks and exact staging. Do not push, release or publish without the maintainer's instruction.
- Add no source comments, docstrings or diagnostic suppressions unless explicitly required.
- Test behavior through existing boundaries. Show new behavior failing before the change and passing after it.
- Commit messages follow Conventional Commits: `<type>(<scope>): <imperative summary>`, subject at most 72 characters, no final period, body only for why.

## Transport

Read before changing it.

- The plug-in opens two `LrSocket.bind` servers (`PluginInfoProvider.lua`): request port 58763 in `mode = "receive"`, response port 58764 in `mode = "send"`. Every message is line-delimited JSON ending in `\n`. Each port takes one client at a time.
- Ports: the server reads `LIGHTROOM_AGENT_REQUEST_PORT` and `LIGHTROOM_AGENT_RESPONSE_PORT` (`server/src/ports.ts`); the plug-in reads `requestPort` and `responsePort` from its Plug-in Manager prefs. Change both sides together.
- Hosts start several servers at once. `Bridge` (`bridge.ts`) elects one leader per port pair through the instance lock; it owns the plug-in sockets and serves the others over local IPC (`broker.ts`: a Unix socket under `~/.config/lightroom-agent/`, a named pipe on Windows, token checked). Followers forward and re-elect when the leader exits. Never `process.exit` on lock contention.
- A receive bind fires `onError` after 10 s without a client. Set a flag in the callback and call `:reconnect()` from the monitor loop; never reconnect synchronously from `onError`, or reconnects storm.
- `onMessage` runs in a non-yielding context, so dispatch runs inside `LrTasks.startAsyncTask`; otherwise catalog gates cannot yield.
- The plug-in answers `ping` with `Contract.VERSION` and `Contract.BUILD` (a digest of the bundle's Lua files and the contract). The build computes that identity once (`expectedIdentity`), renders `Contract.lua` from it and records the build in `dist/plugin-build.json`. A server pairs only with the plug-in it was built with (`pairingOf` in `plugin-pairing.ts`): the record parses, the bundle's `Info.lua` and `Contract.lua` are regular files, `Contract.lua` equals the rendering over the bundle's own Lua, and its `BUILD` equals the record (`validateBundle`). An unpaired server runs no bridge and answers every tool call with its reason: rebuild in a checkout, reinstall in a package. A server promoted to leader checks its bundle again, then the installed plug-in (`admitLeader`); a verified mismatch, or an installed copy it may not replace (`PairingLost`), releases the lock, ends its elections and answers the reason from then on. A paired server refuses every tool call while the plug-in's ping differs from its pairing, naming both (`PluginLiveness` state `incompatible`). The owner's greeting and each follower's hello carry the server's identity (`serverIdentity`: its compiled `VERSION`, a digest of its `dist` scripts and its paired plug-in build); either side answers every call across a missing or different identity with a refusal naming both (`serverMismatch`). An identity with a missing field never equals another (`sameIdentity` in `build-identity.ts`).

## Catalog reads

- Run yielding catalog queries (`getTargetPhotos`, `findPhotos`, `findPhotoByPath`) outside `withReadAccessDo`. A yielding query inside the read gate deadlocks on Windows and wedges the bridge until the server timeout (upstream issues #124, #134). Only non-yielding per-photo reads belong inside; `getAllPhotos` is safe either side. Resolve photo ids before opening any gate. Specs check this with `getQueriedInsideReadAccess()` (`spec_helper.lua`).
- Each SDK getter call costs about 0.1–1 ms. Read a page of photos with `catalog:batchGetRawMetadata` / `batchGetFormattedMetadata` (`PhotoSummary`), a keyword's name and synonyms with one `getAttributes`, and avoid a `LrTasks.pcall` per item.
- Lightroom stores macOS paths in NFD and `findPhotoByPath` does not normalize. Look paths up through `PhotoLookup.findByPath` and compare them with `PathForms.same`; `PathForms.absolute` is the one path rule.
- `catalog:getPhotoByLocalId` returns a dangling photo object, not nil, for an unknown id. `PhotoLookup` keeps only photos whose batched `uuid` read is non-nil.

## Catalog writes and outcomes

The decision is [ADR 0001](docs/adr/0001-one-result-envelope.md). A call's outcome class comes from its write ledger, never from how an error was raised.

- `CatalogWrite.lua` is the only caller of `withWriteAccessDo` and the one place writes are recorded in the request's `Ledger`. Record a write where it can no longer be taken back.
- `CatalogWrite.run` opens a gate that waits `CATALOG_WRITE_WAIT_SECONDS` (generated into `Contract.lua`). It records the gate's title when the gate returns, except when the function raised, when the catalog stayed busy (Lightroom answers `"aborted"` without running the function) or when the function returns `CatalogWrite.NOTHING`.
- `CatalogWrite.call` makes an SDK write inside a gate and records it first, unless `RAISE_INSIDE_GATE` lists the method as observed rolled back by a raising gate. A method not in that table, or one observed on only some receivers, counts as kept. A raise that escapes a gate discards all its journaled writes.
- Some calls are kept despite a raising gate because they are commands, not journal entries: `addPhoto`, `applyDevelopPreset`, `deleteAllEmptyMasks`, applying or deleting a snapshot; `updateAISettings` computes outside the transaction. The table holds the observation behind each entry.
- `CatalogWrite.develop` is the only caller of a writing `LrDevelopController` function and records before the call; `CatalogWrite_spec` scans the plug-in for direct calls. `CatalogWrite.invoke` records any other write outside a gate (undo, Remove from Catalog, virtual copies, treatment, presets, export sessions, files); `createFolder` and `copyFile` record what they create.
- `Ledger:undone` voids entries only after a proving read: one of the store those writes changed, made after they can no longer land, covering everything they may have changed. A controller write lands in the saved settings later, so a Develop-side read proves nothing and such calls answer `unknown`, naming the controller writes.
- `Reply.stopped` is the one rule, for a call (`Reply.outcome`) and for each item of a loop (`Ledger:attempt`): nothing live is `failed`, anything live is `unknown` with "written before this stopped: …". A successful reply with neither data nor unknown items while entries are live carries `written` and becomes `unknown`.
- A read showing a photo's keys changed makes its item `unknown` even with an empty ledger (`DevelopReadBack`).
- Handlers state the problem (`Reply.refuse`, `Reply.notFound`) and never choose the class. A handler returns `Reply.parts{...}` or a plain table, sent as `data`. Specs assert the class with `failedOf`, `unknownOf`, `notFoundOf` and `outcomeOf` from `spec_helper.lua`.
- `server/src/tool-result.ts` derives `outcome` (`done`, `partial`, `failed`, `unknown`) from the reply parts; `isError` is set exactly when the outcome is not `done`. A lost reply is `unknown` for a sent write and `failed` for an unsent call or a read tool.

## Develop sessions, queue and budgets

- `LrDevelopController` acts only on the photo active in Develop. Go through `DevelopSession.lua`: `withPhoto` opens one photo, runs the callback and restores module, view source and selection; `run` is the multi-photo form. A view they cannot restore becomes a reply warning.
- `DevelopSession.selectAlone` opens every photo a Develop session acts on, waiting for that photo alone to be selected (other selected photos are deselected while the tool works, and `restoreView` brings them back). It shows a photo in steps: 2 s in the source on screen, then the photo's own folder at most once per run, then All Photographs, each step polling the exact selection up to its deadline because the grid becomes selectable after the switch; once All Photographs is shown, every later photo polls it for the full deadline with no further switch. `PhotoSources.foldersOf` is the one home of which folders show photos: only catalog folders that exist on disk, since an offline folder may open a modal dialog (unverified), and nil when that cannot be established; `remove_photos_from_catalog` uses it too. `PhotoSources.show` is the one judgement of a switch: one that raises or returns false falls through to the next step (removal falls back to All Photographs and refuses only when that fails too), and `restoreView` and removal's restore report a source they could not put back; removal still restores the surviving selection.
- `PhotoBatch.lua` is the one per-photo loop of every tool that acts on `photo_ids` one photo at a time; `import_photos` (files on disk) and the internal actions `read_settings_by_input` (one row per input) and `read_lens_profiles` (one read gate, no budget) keep their own loops. It owns de-duplication (or, with `duplicates = "refuse"`, one `failed` item for each input of a photo listed twice, naming both inputs), `not_found`, the time budget (`reserveSeconds`, a number or a function of the photos started; once a photo does not fit, it and every later photo that would otherwise start are `remaining` by their input as given, while a held or listed-twice entry keeps its own class), cancellation at the next photo, progress under the gerund title the caller names (`progress`; captions from one batched file-name read; none without a title), each photo's outcome by its own writes, `failed` and `unknown` in input order (stably, by each photo's first input, loop and confirm alike), an optional `held` per entry (`{ reason }` is failed, `{ remaining = true }` is remaining), an optional `fits` asked after a photo's successful work (false makes that photo and every later photo that would otherwise start `remaining`, as the time budget does; a reply limit for work that writes nothing, `get_develop_settings`' 1 MB of settings data), a `prepare` run once before the first photo started (its raise ends the batch), an `around` that wraps the loop and a `confirm` step after it that keeps only confirmed results and may return a `report` of the decided data. `PhotoBatch.reply(batch, dataOf, own)` is the one reply of such a batch: data from `dataOf` only when results remain, the batch's lists, the caller's own problem with or without data, then the confirm's report. `export_photos` builds its own data, because it reports the files of photos that end failed or unknown. `DevelopReadBack.confirm` is the read-back confirm of preset, match, copy and `set_develop_settings_batch`, which gives each confirmed result its stored settings (`stored`) and keeps its written entry; it is built on `DevelopReadBack.classify` and `DevelopReadBack.report`, which single-photo `set_develop_settings` uses too. Photo-list Develop operations (Denoise, process version, Auto, reset, mask batches, treatment, virtual copies, `set_develop_settings_batch`) go through `DevelopBatch.run`: PhotoBatch inside one Develop session, under the operation's `progress` title, with its `confirm` passed through to the reply and data `{ results }` unless the operation names its own `dataOf`; the confirm reads back after the session restored the view. Progress, cancellation and `remaining` belong to these per-photo batches and import; a writer that writes all its photos in one catalog gate has none.
- A read of a photo's develop settings or snapshots while another request's Develop session runs can void that session's controller write: a reset answered done and nothing was reset (Lightroom 16.0). So every plug-in action whose handler reads or writes a photo's develop state or opens a Develop session is marked on its contract or `PLUGIN_ACTIONS` entry: `develop: "drives"`, `"settings"` or `"reads"` (`DISPATCHED_ACTIONS`, `developUseOf`). The tool handler sends a marked action only inside a turn of `DevelopQueue` in the leader, shared by every client, in arrival order. A server-run contract marked `develop` holds one turn across all its requests; an unmarked one takes a turn for each marked request it sends, so `get_photo_detail`'s crop read waits and its render does not, and `get_photo_metadata` sends its lens-profile read (`read_lens_profiles`, marked) only when asked while its metadata read (`read_photo_metadata`) does not wait. Catalog reads, other catalog writes and renders run alongside. A call that gets no turn within its budget fails without sending anything. A request that times out inside a turn keeps the turn until its late reply or the 60 s grace, even when a server-run tool turns the timeout into a reply. After that grace, or after the connection or the leader changes, a Lua task of the old call can still overlap a newly admitted read; `DevelopSession`'s single-flight refusal stops only a second Develop driver. A test in `tool-handler.test.ts` follows each action's handler through the plug-in's Lua (`tests/helpers/lua-reach.ts`): a function-level call graph of module and local functions, requires and aliases. It fails on a dispatched handler it cannot find, and on an unmarked action that reaches a read (`:getDevelopSettings`, `:getDevelopSnapshots`), `DevelopSession.run`, `CatalogWrite.develop`, `LrUndo.undo`, or a develop write method named as a method, a field or a string (`applyDevelopSettings`, `applyDevelopPreset`, the snapshot writes, `updateAISettings`, `deleteAllEmptyMasks`, `quickDevelopSetTreatment`, `createVirtualCopies`), which covers `CatalogWrite.call`, `CatalogWrite.invoke` with a function value and `PhotoWrites`' method names. It cannot follow a call through an object's method (`obj:fn()`) or a function looked up by a computed key.
- A pending Develop edit overwrites a saved-settings write about 2 s later. Develop's pending edit is committed before saved develop state is read or written: at dispatch (every action but `ping` and the thumbnail reads `render_preview` and `render_duplicate_preview`, `PluginInfoProvider.lua`), before every `CatalogWrite.run` gate and `CatalogWrite.invoke` call, and at the end of a Develop session body that made controller writes (`DevelopSession.run`); Auto commits its write and polls the saved settings until they settle. Reset commits its write and reads nothing for `RESET_LANDING_WAIT_SECONDS`: a landed reset reaches the saved settings about 2 s after the call, and a read before that can void it. The reset checks that its photo is still the active one right before the controller write, so a photo the user switched to is never reset. One read then decides the photo: `reset` only when an edit a reset clears changed (`DevelopReadBack.changedEdits`: a develop key, the camera profile or the Look's name or amount, or fewer masks, spots or Enhance filters), never on Lightroom's derived Upright and mask data; otherwise, or when the read returns nothing, `unknown`, with no retry. An unedited photo reads the same before and after a landed reset, so that `unknown` says the photo may have had nothing to reset and asks for a read before retrying. `DevelopSession.commitPendingEdits` is the one commit, and `CatalogWrite_spec` scans for any other. A commit with nothing pending adds no history step (Lightroom 16.0). An edit the user makes during the call can still be lost.
- `DevelopSession.requireControllerFunctions` is the one gate for a controller function a Lightroom version may lack. The plug-in declares Lightroom Classic 15.0 as its minimum (`Info.lua`); only `apply_denoise` checks for a function, because Denoise is outside the SDK.
- Snapshot apply and delete are Develop-module commands that do nothing elsewhere, so `HandlerSnapshots.lua` runs them inside `withPhoto`. Snapshots are stored per master: deleting one through a virtual copy deletes it for the master and every copy.
- A contract with `duration: "long"` gets the long timeout, every other tool the quick one (`TIMEOUT_MS_BY_DURATION`, decided only in `createCallToolHandler`). Each request carries `budget_ms`; handlers use `RequestContext` (`timeLeft()`, `stopping(reserveSeconds)`, cancellation, `report()`) and stop starting items when one more would not fit. No plug-in constant mirrors the server timeout.

## Develop keys

- Develop keys have one home, `server/src/develop-keys.ts`: `DEVELOP_KEYS`, `DEVELOP_RULES` and `LOCAL_KEYS`. Schemas are generated from it and the build writes it into `Contract.lua`. A key enters only with live evidence: range, write, read-back after normalisation, rendered effect. A key's `derives` lists the keys Lightroom was seen to write from it (incremental white balance on a non-raw photo, the tone curve's name); `copy_develop_settings`' final read expects them (`DevelopReadBack.derivedFrom`).
- `set_develop_settings` runs on the server (`develop-write.ts`): it rounds to precision, checks rules against stored values and writes through the internal `write_develop_settings` action; keys another tool writes and point-curve shapes are refused by its contract rules. The stored values come from the internal `read_settings_by_input`, one row per input in order (an alias shares its photo's row): the values, a failed read, not found, or remaining past the budget. `set_develop_settings_batch` sends every input to `write_develop_settings_batch`, marked `refused` or `remaining` when it is not to be written, so PhotoBatch's alias rule sees every input; a lost write reply keeps that split by input.
- Lightroom normalises a write within about a second, and the read right after the gate only echoes the input. `DevelopReadBack.lua` reads back after that second and reports `adjusted`; it stops reading when less than `REPLY_SECONDS` of the budget are left (time only, not cancellation), and a written photo it did not reach is `unknown`. A written key absent before and after is `not_stored` with a warning; one present before and absent after is `unknown`. Every read-back entry carries its ledger interval: `DevelopReadBack.entry` builds one, and `DevelopReadBack.attempt` marks the interval around a write's work, catches its raise as the entry's error and keeps the before-state, so the final read can still find a changed key. An entry's `kept` (match's recovery snapshot) is named on every unknown item whose read-back ended in an error: the work raised, the final read failed or missed the deadline, or the comparison failed; an absent-key reason ("Lightroom shows no X after the write") keeps its exact text, because its read succeeded and the photo's state is known. Only preset, match and copy catch through `attempt`; in single `set_develop_settings` and the settings batch a raise reaches the call or the batch loop, as before.
- `DevelopReadBack.saved` is the only caller of `photo:getDevelopSettings()` (a `DevelopReadBack_spec` scan). A nil answer raises, naming the photo, so a read that returned nothing fails that photo and never reads as empty settings: no absent key, crop, mask, Enhance filter or profile is derived from it.
- Point curves, global and mask, take at most `POINT_CURVE_MAX_PAIRS` (16) points. Lightroom keeps a longer global curve only as an Extended companion that then wins over plain writes, so `DevelopCurves.lua` reads the Extended field first and writes both.
- `describe_develop_keys` is the only reader of `LrDevelopController.getRange`. Certification compares the static ranges and fails on a stale one without touching mask admission.

## Masks

Decisions: [ADR 0002](docs/adr/0002-mask-write-admission-by-certification.md) (admission by certification) and [ADR 0003](docs/adr/0003-masks-addressed-by-id-in-the-saved-settings.md) (addressing by id).

- Address masks by photo and `CorrectionID` in the saved `MaskGroupBasedCorrections`, not through Develop's selection. That setting is undocumented: write it only through `GuardedMaskWrite.lua`, never directly.
- `GuardedMaskWrite.submit` is the one whole-array write: commit pending Develop edits, build on a read taken inside the gate, write, read back with the caller's comparison, and restore on a mismatch through `GuardedMaskWrite.restore`. The restore writes the previous array back unvalidated and confirms it with an exact read. It refuses, writing nothing, while a mask or top-level component on the photo has no id yet (`requireNamed`). A full copy that first writes a target's process version runs `GuardedMaskWrite.precheck` before that write: admission under that version, then the ids, then the format of the masks it will write, through the same functions apply uses.
- `GuardedMaskWrite.apply` is `submit` behind admission, for writes that construct or change entries. It checks the pinned format only on what the call constructs or changes (`plannedEntries`), compares constructed numbers within 1e-5, and requires every untouched entry back exactly: those are Lightroom's own data. It names every entry and top-level component it adds that has no id (`CorrectionID`/`MaskID`, an uppercase GUID from `LrUUID`) and requires the names back; Lightroom keeps them.
- Value edits and deletions construct nothing and need no admission. `MaskValues.lua` owns sliders, local curves and Point Color by id, with no Develop session. It skips an unchanged request, sets `CorrectionActive` (warning when a hidden mask is shown) and demands an exact read-back of the whole array (`JsonValue.differences`).
- Admission (`MaskWriteAdmission.lua`): always on a catalog whose folder holds `lragent-live-catalog.json`; elsewhere only when `~/.config/lightroom-agent/mask-certification.json` names the running build from `LrApplication.versionTable()` and the photo's process version. No build, no admission. The record does not bind the plug-in revision: rerun certification after changing the plug-in.
- Only `tests/e2e/live/certify-mask-writes.mjs` writes the record, after its suite passes on the throwaway catalog, or a `--rejudge` of a saved run file, without Lightroom, when every step passes under the thresholds it applies (the shipped ones, overlaid by the saved run's own and then by any `--threshold` overrides; the record names the result). After a Lightroom update, constructing writes stay refused until it reruns. Widening the pinned format needs a live check. `GuardedMaskWrite.formatProblems` feeds `schema_problems`; certification reads it, admission does not.
- Lightroom stores slider values to six decimals (`STORED_MASK_DECIMAL_PLACES`) and colour-grade keys as whole numbers. `LocalSliders.storedOf` rounds before the write; replies report stored values. A new local slider is one `LOCAL_KEYS` entry. The schema is the only range check on a local slider write.
- Point Color: the four edges of every range must be ordered or Lightroom drops the whole list (`MaskPointColors.requireOrderedRanges`). Deleting the last swatch or clearing removes both `LocalPointColors` and `LocalColorVariance`, since Lightroom drops empty arrays.
- `MaskSelection.lua` owns Develop's mask list for `invert_mask` and the live ranges of `describe_develop_keys`: `readMasks` waits up to 5 s until Develop lists as many masks as the saved settings hold, then refuses. `withMaskSelected` refuses when the selection moved; `keepingSelection` is the one restore. Invert's copy waits for the saved mask, then writes by id.
- Argument laws of the gradient, range and brush tools are contract rules in `server/src/tool-contracts.ts`. `GradientGeometry.lua`, `RangeMaskGeometry.lua` and `BrushStrokes.lua` refuse only on derived or stored values. `plugin/spec/CertifiedGeometry_spec.lua` pins the stored geometry of certified inputs byte for byte.
- A colour range the plug-in constructs holds exactly one `PointModels` entry: a two-entry write crashed Lightroom and crash-looped the catalog on reopen. Lightroom-authored multi-sample ranges are resent unchanged.
- A colour range's `l a b` is Lightroom's per-photo ranking of the sampled colour, not sRGB; Lua cannot compute it. `create_range_mask` takes it verbatim or copies it with `copy_sample_from`; busted specs hold Lightroom-authored samples as ground truth.
- A depth range is refused when the read-back lacks `LuminanceDepthSampleInfo` (no device depth); Lightroom replaces a band narrower than 0.01 with its default.
- Brush Size is a screen size that changes with zoom, so only `radius` is exposed. Feather maps to stored `Radius` and `CenterWeight` through `BrushFeather.lua`. `MaskValue` 0 is an erase stroke.
- Mask geometry is stored in the stored frame; tools take and return positions in the displayed frame. `ImageFrame.lua` is the one conversion. Upright, Transform and manual distortion have no inverse, so such writes carry a warning. A crop angle combined with a non-default orientation is not yet checked live.
- `set_crop`: `HandlerCrop.plan` computes the keys, `server/src/crop.ts` writes them through the `set_develop_settings` rounding and rules, then reads them back.

## AI masks

- `createNewMask('aiSelection', 'people'|'landscape')` makes no mask because Lightroom waits for a menu pick. All AI masks (Subject, Sky, Background, People and Landscape parts) are written as seed components through `GuardedMaskWrite.apply`, then computed. Lightroom ignores written person ids and masks the first person.
- `AIMaskData.lua` lists the fields Lightroom computes per photo (digests, sizes, origin, reference point, `ErrorReason`). They are never compared or copied (`isComputed`, `withoutComputedData`), so a copied mask is recomputed for its target.
- `AIMaskCompute.run` is the only caller of `photo:updateAISettings()` and the one judgement of AI masks. It applies the optional guarded write, computes in its own gate, then polls until nothing is pending, up to `AI_MASK_COMPUTE_WAIT_SECONDS`.
- Outcomes: a compute gate never entered restores and refuses. Anything still pending at the limit is `unknown`, and nothing more is written to the photo: a write during a compute can freeze Lightroom. An own entry with a non-zero `ErrorReason` is restored and refused (`ErrorReason` 1 is "nothing found", with no modal alert).
- The call's own entries are the ones it wrote: the `CorrectionID`s new to the photo, a combine's added component, or all of them for a full copy. Entries already failed before the call, and existing AI masks that changed, only produce warnings.
- The compute is photo-wide: it can also update Enhance, Remove areas, Lens Blur depth and an adaptive profile. After the masks are restored, the compute is voided only when the whole develop settings equal the read taken inside the mask write's gate; otherwise the call is `unknown`, naming the changed keys.
- Callers: `create_mask`, `create_mask_batch`, `combine_mask`, a full `copy_develop_settings` and `apply_develop_preset` (each photo once; for a preset, any outcome but done is `unknown` with the preset kept). A digest proves computation, not useful coverage.
- In render checks, wait for the expected change instead of trusting one early preview. On a raw, a parametric mask write re-renders the photo with texture-level differences even when neutral, so compare regional means, never single pixels.

## Profiles

- A profile is a family of saved keys Lightroom builds together: `CameraProfile`, its digest, the profile Look (`Look`) and the `Table_*` payloads it references, `ConvertToGrayscale`, Lightroom's treatment memory (`ToggleStyleDigest`, `ToggleStyleAmount`) and `MissingCameraProfile`. `ProfileLook.lua` owns that family, `set_profile`'s refusals and its read-back: by name, anything outside the family that changed makes the call `unknown`, naming the keys; for an amount, anything but the Look's amount. No saved read carries `CameraProfileDigest`, and the stored Look is Lightroom's own form of the profile, not the preset's `getSetting()` (Lightroom Classic 16.0.1), so neither is compared.
- The plug-in never builds a Look. By name, `set_profile` applies the matching preset in Lightroom's `PROFILE_PRESET_GROUP`, selected by group and name through `developPresetFolders` (the uuid Lightroom lists differs from the file's) and accepted only when its file carries the plug-in's preset UUID and `getSetting()` declares the profile's Look UUID; two presets of that name, or a foreign one, are refused. Lightroom then resolves the profile against the photo's own camera, with its digest and tables (Lightroom Classic 16.0.1). The refusals and the before-read happen inside the write gate that applies the preset, and the read-back waits `PROFILE_SETTLE_SECONDS` (2 s, what S2 waited after a paste; 1.5 s after a preset apply was also settled). Only the names a live check proved against Lightroom's own pick are offered (`ADOBE_RAW_PROFILES` in `lightroom-tables.ts`). A black and white RAW is refused: a colour profile applied over it changes the treatment and the keys the conversion keeps.
- An amount rewrites the Look read inside the write gate, whole, with the new `Amount`. Lightroom stores an amount on a Look that declares `SupportsAmount = false` all the same, so that refusal is ours; a Look without the field takes an amount. An Adaptive Look (`isAdobeAdaptive`) is left alone.
- `copy_develop_settings` moves the profile as one unit (`PROFILE_UNIT` in `settings`, and part of a full copy, whose copied keys never include the family): the source's `copySettings("custom", { look = true })`, then the target's `pasteSettings()` through `CatalogWrite.invoke`, outside a catalog gate (both ran there, Lightroom Classic 16.0.1), before anything else is written to that target. Lightroom owns the Look, its tables and the digest; the paste overwrites Lightroom's Develop clipboard. `ProfileLook.leftReason` decides from the file kind (`fileFormat`), the formatted camera model, the treatment, an Adaptive Look and `CameraModelRestriction`; a colour paste onto black and white changed the treatment and 34 other keys, so treatments must match. The read after the paste requires the source's profile and nothing outside the family changed; otherwise the target is `unknown` and gets nothing more. The final read requires the treatment unchanged, the expected profile (the source's when pasted, the target's own otherwise) and every key the copy did not write unchanged; keys Update AI Settings changed while computing copied AI masks are named with `AIMaskCompute.changedMoreText` instead. Every such comparison skips Lightroom's bookkeeping (the writer stamp `Version`, kept in `SettingsChanges`). In every such comparison an absent key and an empty table are equal (a white-balance copy onto a JPEG flagged `MaskGroupBasedCorrections` moving between the two, Lightroom Classic 16.0.1), and a flagged key shows what it was and is now; `SettingsChanges.between` is that comparison, also behind the report of what Update AI Settings changed.
- `photo:getDevelopSettings()` lists no `Table_*` key even when the Look references one (Lightroom Classic 16.0.1).

## Other Lightroom traps

- `photo:quickDevelopSetTreatment` ignores its receiver and acts on Library's selection, which Lightroom can refuse while its command status is stale. `HandlerTreatment.lua` selects the photo alone, dispatches up to twice and answers by the read.
- Develop blocks ordinary preview processing for its active image, and the thumbnails Lightroom still hands out for it can be stale or an enlarged low-resolution live pixmap; a Library round trip returns such a pixmap too, since leaving Develop stops waiting for the best one, and Develop re-blocks the image on return (Lightroom 16.0). So `HandlerPreview`'s `thumbnailOf` checks module and target before every `requestJpegThumbnail` and declines Develop's target with the cause `active_in_develop`, which `preview-item.ts` answers failed with the hint naming `render_photo`. The preview tools stay reads: they never export, and the plug-in's dispatch commits no pending edit for their actions. `render_photo` is the write that renders any photo whole by an export rendition; it and `get_photo_detail` share one export-render home, the internal action `render_source` (`HandlerExport.renderSource`, a rendition at `long_edge` or a full-size detail render) and, on the server, `withRenderedFile` in `photo-detail.ts`, which reads the file, removes its folder and warns when it cannot. A no-pixels answer for any other photo is still asked again every second within the deadline.
- Export presets (`ExportPresets.lua`) are `.lrtemplate` files parsed as literal tables, never run. A wrong-typed setting can hang the session silently, so `invalidSetting` marks it unusable.
- Each photo gets its own `LrExportSession`, so sequence numbers are continued per photo. The session ignores `size_percentage` and truncates `size_megapixels`, so both become a per-photo long edge; `longEdge` ignores width. `LR_jpeg_quality` runs 0–1.
- Parallel export sessions write nothing, so one export of this plug-in (`export_photos`, `get_photo_detail`, `render_photo`) runs at a time; the lock lapses 300 s after the last photo started, and an export started from Lightroom's menu does not take it. An "AI Updates Recommended" dialog blocks the call; each session is recorded before it starts, so a cancelled photo is `unknown`.
- Lightroom runs `LrInitPlugin` only when its window is first activated: a background launch starts no server until Lightroom comes to the front.
- Reload Plug-in does not reliably stop the old task. `PluginShutdown.lua` stops the old loop; when Lightroom skips it, the old loop exits on a foreign token (`PluginServerPolicy.isSuperseded`). Until then the new binds fail with `failed to open`.
- Reload Plug-in does not see a `.lua` file added after Lightroom started; the plug-in is disabled. Restart Lightroom after adding a file.
- The plug-in loads every handler module when it initialises (`HandlerLoads.loadAll` in `PluginInit.lua`, on load and on Reload Plug-in), and modules require each other only at the top level (a `PluginInfoProvider_spec` scan), so a bundle replaced on disk does not mix into a running plug-in. `HandlerLoads` keeps each module's first load result: a module that fails to load is logged once, and every one of its actions answers with that first failure while the rest keep working; a failure raised by a dependency is recorded under the module whose load reached it.
- Only the holder of the instance lock installs: a stdio server's elected leader, after its pairing check (`startLeader`, `admitLeader`), and `install-plugin`, which checks its pairing and holds the instance lock of its port pair, refusing while a running server owns it. A follower and a `call` never install. Versions are ordered (`compareVersions`, SemVer precedence) and builds are not: `planInstall` classifies the installed copy as absent, same build, older, newer or unordered (the same version with another build, or a version that cannot be read). A server leads only over an absent, same-build or older copy; over a newer or unordered one, `admitLeader` throws `PairingLost` with the reason, for a stdio leader and a `call` alike, and leaves the copy alone. A failure while planning is logged and the server leads without installing. `install-plugin` replaces every class and names a move to an older version. An install first puts back a bundle a killed swap left aside as `.replaced` and clears other leftovers, then works where this plug-in is installed (Modules or Plugins, else Modules): it leaves a bundle with another toolkit id alone and refuses while a `LightroomMCP.lrplugin` is installed, because it binds the same ports. Otherwise it copies the bundled plug-in's regular files into a private `.installing-<pid>-<time>` folder and publishes that copy only when it validates against the pairing (`validateBundle`). An installed bundle whose Lua files equal the copy's, line endings aside, is current; any other is renamed aside to `.replaced`, the copy renamed into place and the aside removed, or put back when the copy cannot be moved. A replacement of the same `BUILD` is reported as a repair. Whenever this plug-in ends up installed, current or repaired, the install also writes the profile presets `set_profile` applies (one per `ADOBE_RAW_PROFILES` entry, holding `CameraProfile` and a stubbed Look reference, no Baseline) into Camera Raw's settings folder (`profilePresetsDir`). It plans both files before writing either: an identical file stays, a file carrying the plug-in's preset UUID is replaced through a staged file and a rename, and any other file or link at that name is left and reported; a write error is reported beside the plug-in's own result rather than failing it. Lightroom registers the presets when it starts. The Windows folder is unverified. The bundled plug-in is looked for only where a distribution puts it: the checkout's `plugin/`, then beside `dist/` (npm) or beside `server/` (mcpb). Plug-in log: `~/Documents/LrClassicLogs/LightroomAgent.log`.

## Adding a tool

- Add its contract in `server/src/tool-contracts.ts` with `run: { plugin: "HandlerX.fn" }`, or `run: { server }` for a server-run tool; internal plug-in actions go in `PLUGIN_ACTIONS`. Put the handler in `plugin/LightroomAgent.lrplugin/Handler*.lua` and declare new SDK globals in `lightroom.yml`.
- Mark the action `develop` when its handler reads or writes a photo's develop state or opens Develop: `drives` when it opens a photo in Develop or calls `LrDevelopController`, `settings` when it writes saved settings without either (a mask batch that runs through `DevelopBatch` without switching to Develop is `settings`), `reads` for a read. The queue treats the three alike; the value states why the tool waits and selects its published sentence. Mark a server-run tool only when its requests must share one turn, as a read before its write does. A new SDK getter or write of develop state joins the scan's list in `tests/helpers/lua-reach.ts`.
- Run `npm run build` to regenerate `Contract.lua`, whose `BUILD` changes with any plug-in Lua file; a Vitest test fails while it is stale, so rebuild after a Lua edit.
- `tools/call` refuses a name with no contract, so internal actions such as `write_develop_settings` are reachable only over the raw TCP probe.

## Live kit

`tests/e2e/live/README.md` holds the bootstrap, fixtures, helpers and known traps. Its safety rules bind:

- Live runs need the user's permission and exclusive control of Lightroom; one agent writes at a time.
- The guard (`requireThrowawayCatalog()` in `lib/catalog-guard.mjs`) refuses catalogs under `~/Pictures/Lightroom`, then accepts a catalog whose folder holds `lragent-live-catalog.json` or that `LRAGENT_LIVE_THROWAWAY_CATALOG` names. It cannot recognise a personal catalog stored elsewhere: check the catalog before opting it in.
- One-shot `mcp-runner.mjs tool` calls and `node server/dist/index.js call` are not guarded.
- `mise run live:setup` switches Lightroom away from the open catalog to a new one.
- Never commit a `.lrcat` or a photo whose licence does not allow redistribution. Bundled fixtures carry their source, licence and hash in `tests/e2e/live/fixtures/SOURCES.md`.
- Back up the installed bundle outside `$TMPDIR` before installing a candidate (`install-bundle.mjs` does it) and restore it afterwards.
- A listening socket does not prove requests work: confirm with a tool call. Never force quit Lightroom or remove another process's socket.
- Make temporary collections and keywords uniquely named, delete only those, and confirm the catalog's original state afterwards.
