# Lightroom Agent

Local fork of Automaat/lightroom-mcp. Build a broad, verifiable Lightroom Classic API for agents through one backend used by MCP and a scriptable CLI; selectively port verified capabilities from znznzna/lightroom-cli. The existing sibling photo-workflow workspace is separate.

The aim is a better tool than the existing ones, judged by the quality of the photographs an agent can produce with it and by how much of Lightroom it can drive. Those two outrank token cost, development effort and closeness to upstream. Its first user is the owner, editing their own photographs and publishing them to their channel and social networks; work is ordered by what that needs next.

## Ownership

This codebase is yours: what it's for and how it's built are your call, and you'll keep building on it. That includes the code inherited from upstream.

Nothing here is kept for compatibility. The API has one consumer, the owner's photo workspace (its local path is in the untracked CLAUDE.local.md), and its instructions change in the same step as the API. A tool's shape, name, default or vocabulary stays only while it is the best one for the agent that calls it; "it was like this before" is not a reason. Upstream is a source of fixes to take, not a shape to stay close to.

Outside your ownership: the owner's personal catalog and photographs, what is installed into the owner's Lightroom and when a live session takes it over, publication (remote, push, release, the MIT license and upstream history), and the order of work the owner has set. Those need the owner's word, and the fork rules below govern them.

## Fork working rules

- Preserve upstream history and the MIT license.
- Keep AGENTS.md as the symlink to this authored file. Preserve the upstream operational constraints below; verify behavior claims against the current source before relying on them.
- Photographic guidance and image-quality experiments live in the owner's photo workspace; technical API facts, contracts and mechanics live here. API work supplies capabilities, stable identities, render provenance and verifiable outcomes; it must not silently turn an experimental score into a culling rule.
- The bundled `skills/raw-photo-lightroom-preset` is upstream content shipped as the MCP prompt and mcpb prompt. Do not install it into the owner's agent environment: its trigger overlaps the `lightroom-photo-workflow` skill in the owner's photo workspace.
- Tool contracts and access policy are shared by CLI and MCP. Reuse the existing bridge and Develop session lifecycle; do not add a second Lua protocol or catalog model.
- Default to offline development and tests. Live tests require an isolated disposable catalog and coordination with any active photo workflow. Do not install/reload a plug-in, restart Lightroom, switch the live catalog, or alter personal photos as a side effect of development or tool discovery.
- For undocumented APIs, distinguish a discovered symbol, callable signature, persisted effect and verified render. Widen version/schema guards only with evidence from the exact Lightroom version.
- Keep one mutating worker; delegate independent read-only investigations. Parent owns integration, final checks and exact staging. Do not push or publish without the owner's instruction.
- Add no source comments/docstrings or diagnostic suppressions unless explicitly required. Test behavior through existing boundaries; show new behavior failing before implementation and passing afterwards.
- Read build/test commands from server/package.json and CI configuration. Run relevant fresh checks after the final edit; never substitute a live-test-kit unit run for Lightroom validation.

## Layout

- `server/` — TypeScript MCP server (ESM, NodeNext). Stdio transport for Claude + raw TCP client to plugin sockets.

## Architecture (read before changing transport)

Plugin opens **two LrSocket binds** as servers; MCP server connects to both.

- Plugin :58763 (default) in `mode='receive'` — server writes line-delimited JSON requests
- Plugin :58764 (default) in `mode='send'` — server reads line-delimited JSON responses
- Frame: `\n` terminator on every message (LrSocket buffers until newline)
- Plugin allows **one client per port at a time**. MCP server holds a persistent connection.
- Hosts spawn several bridges at once (Claude Desktop: chat + Cowork/Code shared pool, #238). `Bridge` (`server/src/bridge.ts`) elects one per port pair via the instance lock: the leader owns the plugin sockets and serves tool calls over local IPC (`broker.ts`: Unix socket in `~/.config/lightroom-mcp/`, named pipe on Windows, plugin token checked); followers forward, and re-elect when the leader exits. Never `process.exit` on lock contention.
- `LrSocket.bind` in `mode='receive'` has a 10s no-client timeout that fires `onError`. Plugin auto-calls `:reconnect()` from a monitor loop in response. Reconnect storms are prevented by setting flags in callbacks and acting on them in the loop (never `:reconnect()` synchronously from `onError`).
- `onMessage` runs in non-yielding context — handler dispatch must be wrapped in `LrTasks.startAsyncTask` so `catalog:withReadAccessDo` can yield.
- Catalog queries that yield (`getTargetPhotos`, `findPhotos`) must run **outside** `withReadAccessDo`. Nesting a yielding query inside the read gate deadlocks on Windows: the task yields to the UI thread holding the gate, never returns, never releases it, wedging the bridge until the server timeout (#124/#134). Only non-yielding per-photo metadata reads belong inside the gate. `getAllPhotos` is a non-yielding enumeration, safe either side. `PhotoLookup` resolves paths with `findPhotoByPath`, a catalog query, so handlers resolve photo ids before opening either gate. Specs guard this via `getQueriedInsideReadAccess()` in `spec_helper`.
- Catalog writes go through `CatalogWrite.lua`, the only caller of `withWriteAccessDo` and the one place a call's writes are recorded. Each request's `RequestContext` holds a write ledger (`Ledger.lua`), and the outcome class comes from it, never from how an error was raised. `Reply.stopped` is the one rule, for the call (`Reply.outcome`) and for each item of a multi-photo loop (`Ledger:attempt`): nothing live in the ledger is failed (`effect: "none"`, or `not_found`), anything live is unknown and the message ends "; written before this stopped: …". The same holds for a successful return: a reply with neither data nor unknown items while the ledger holds a live entry (an export folder made before every photo was left for later) carries `written` and the server answers unknown (`ReplyParts.written` in `tool-result.ts`). An effect is recorded where it can no longer be taken back. `CatalogWrite.run` opens the gate (`timeoutParams`, waits `CATALOG_WRITE_WAIT_SECONDS`, 10, generated into `Contract.lua`) and records its title when the gate returns: nothing when its function raised, when the catalog stayed busy (Lightroom answers "aborted" only without running the function, observed on 16.0) or when the function returns `CatalogWrite.NOTHING`. `CatalogWrite.call` makes an SDK write inside a gate, and only there, and records it before the call unless `RAISE_INSIDE_GATE` holds the method as observed rolled back by a raising gate. That table carries each observation: on 16.0 develop settings, rating and GPS through `setRawMetadata`, collection sets, collections, smart collections, photos added to and removed from a collection, keyword creation, attributes, add and remove, snapshot creation and plug-in properties are rolled back; `addPhoto`, `applyDevelopPreset`, `deleteAllEmptyMasks` and applying or deleting a snapshot stay (they are commands of their own, not entries of the gate's journal; the snapshot commands belong to the Develop module and do nothing outside it, which is why `HandlerSnapshots.lua` runs them inside `DevelopSession.withPhoto`, and snapshots are stored per master, so one deleted through a virtual copy is deleted for the master and every copy), and `updateAISettings` computes outside the transaction. A raise that escapes the gate discards every journaled write of that gate, however many (static analysis; one write per gate observed). A method that is not in the table counts as kept, and so does one whose receivers were not all observed (a collection's `delete`: only a regular collection was tried). `CatalogWrite.develop` is the only caller of a writing `LrDevelopController` function and records before the call (`CatalogWrite_spec` scans the plug-in for direct calls); `CatalogWrite.invoke` records any other write outside a gate (undo, Remove from Catalog, virtual copies, treatment, a plug-in preset, each export session, the metadata JSON), `createFolder` a folder it made and `copyFile` a file it copied. `Ledger:undone` voids the entries since a mark, and only a proving read licenses it: one that reads the store the voided entries wrote, after those writes can no longer land, and covers everything they may have changed. The callers are `GuardedMaskWrite.restore` (the whole mask array read back exactly, which voids the mask write and the restore's own gate and nothing else), `AIMaskCompute` for its compute (`photo:updateAISettings()` also updates stale Enhance filters, Remove areas, Lens Blur depth and an adaptive AI profile and saves the whole settings table, by static analysis of 16.0; so after the masks are restored the compute is voided only when the photo's whole develop settings equal the read taken inside the mask write's gate, `GuardedMaskWrite.submit`'s `settings`, and otherwise the call answers unknown naming Update AI Settings and the keys that changed; whether Lightroom's save leaves every other key identical when only the new mask was stale is not yet observed), `createFolder` (the topmost folder the call created is gone), `copyFile` (no file at the target), the detail folder and the metadata JSON of `HandlerExport.lua`, and an import whose photo the catalog does not hold after `addPhoto` raised. A controller write lands in the saved settings later, so a controller-side read proves nothing: invert's copy, a spot rollback and Denoise's revert void nothing and answer unknown, naming the controller writes. A read that shows a photo's keys changed makes its item unknown even with an empty ledger (`DevelopReadBack`). Handlers state the problem (`Reply.refuse` is the readable form, `Reply.notFound` a missing input) and never choose the class; specs assert it with `failedOf`, `unknownOf`, `notFoundOf` and `outcomeOf` (`spec_helper.lua`), which take the class from `Reply.outcome`.
- Every SDK getter call (`getRawMetadata`, `getFormattedMetadata`, `LrKeyword` getters) costs ~0.1-1 ms; per-call overhead dominates handler time on large catalogs. Read photo fields for a page with `catalog:batchGetRawMetadata` / `batchGetFormattedMetadata` (`PhotoSummary`), read keyword name and synonyms with one `getAttributes`, and avoid `LrTasks.pcall` per item (~1 ms each).
- Lightroom stores a macOS path in NFD and `findPhotoByPath` does not normalize. Path lookups go through `PhotoLookup.findByPath` and comparisons through `PathForms.same` (`PathForms.lua` holds a composition table, an NFD map with its recomposition exclusions, beside hand-written lookup and path-rule functions; `PathForms.absolute` and `canonical` are the one path rule and refuse), so an NFC path finds its photo.
- `catalog:getPhotoByLocalId` returns a dangling photo object, not nil, for an unknown id; its metadata reads return nil. `PhotoLookup` keeps only photos whose batched `uuid` read is non-nil.

- `LrDevelopController` (denoise, masks) only acts on the photo active in Develop. Handlers that need it go through `DevelopSession.lua`: `withPhoto` opens one photo in Develop, runs a callback, then restores module, view source and selection; `run` is the lower-level form for multi-photo flows; both take the request context and add a view they could not restore to the reply's warnings. Photo-list Develop operations (Denoise, process version, Auto, reset) go through `DevelopBatch.run`, which resolves and de-duplicates the inputs and owns `not_found`, the time budget, cancellation, progress and each photo's outcome (failed or unknown by what the ledger holds for that photo; the batch goes on to the next photo). One Develop-driving call runs at a time. Mask handlers live in `HandlerMasks.lua` (listing) and `HandlerMaskDelete.lua` (deleting: `delete_masks` removes entries and components by id from the saved array with an exact read-back of what remains, an entry whose last component goes is removed, no Develop and no certification since it constructs nothing; `delete_empty_masks` uses `catalog:deleteAllEmptyMasks`, LrC 14+, which removes groups without components and keeps a mask with a component whether adjusted or not); `DevelopSession.requireControllerFunctions` is the one gate for a controller function a Lightroom version may lack, and it refuses; `requireMaskApi` (LrC 11, SDK 11.0) is one call of it. Lens Blur and Remove spots also refuse by version number below 13.3 and 14.1. Mask values (the `local_*` sliders, local tone curves, Point Color swatches) are owned by `MaskValues.lua` and addressed by photo and the mask's `CorrectionID` in the saved `MaskGroupBasedCorrections`, with no Develop session, masking tool or selection: `read` decodes sliders as stored field times scale (absent is neutral), curves through `MaskCurves.ofEntry` (the `Extended*` field first, then the plain `"x,y"` strings, else linear) and swatches through `MaskPointColors.fromStored` (19 numbers per swatch beside `LocalColorVariance`); `write` and `copy` share `submitEdits`, which run through `GuardedMaskWrite.submit`, skips an unchanged request without a write, builds on a snapshot read inside the write gate, sets `CorrectionActive` true (a hidden mask is shown again, with a warning) and demands an exact read-back of the whole array (`JsonValue.differences`: every named field as written, everything else unchanged down to ids, digests and dabs), restoring and refusing otherwise. `GuardedMaskWrite.submit` is the one whole-array write: it commits Develop's pending edits first when Develop shows the photo (`DevelopSession.flushIfShowing`, also called before every develop-settings gate of `HandlerDevelop`, inside a running session too; a pending edit otherwise overwrites the saved write about 2 s later, seen on 16.0, and for the same reason a Develop session that made a controller write commits what it left pending before it restores the view), builds inside the gate, reads back with the caller's comparison and restores on a mismatch through `GuardedMaskWrite.restore`, the one restore (the previous array written back as Lightroom's own data, not validated, and confirmed by an exact read of the whole array; `AIMaskCompute` uses it too); `apply` is `submit` behind the admission, for writes that construct or change entries: it validates against the pinned format only what the call constructs or changes (`plannedEntries`; a changed entry in its changed fields and components), and every entry the call leaves alone must come back exactly, since those are Lightroom's own data and a whole-array write resends them byte-identically (observed on every mask kind tried, a multi-sample colour range and an empty group included); value writes and deletions construct nothing and need no admission. The one local slider table is `LOCAL_KEYS` (`server/src/develop-keys.ts`: SDK name, range published in every adjustments schema, stored correction field and scale, `storedDecimals`, neutral value when not 0): Lightroom stores slider numbers to six decimal places (`STORED_MASK_DECIMAL_PLACES`) and the colour-grade keys as whole numbers, `LocalSliders.storedOf` rounds before the write and replies report the stored value; the build generates `Contract.lua`, which `LocalSliders.lua` reads, so a new local slider is one entry. get_mask, set_mask_adjustments, set_mask_curves and edit_mask_point_colors are `MaskValues` calls; guarded creates put sliders into the entry they build (`MaskValues.storeAdjustments`); invert's copy waits until Lightroom saved the new mask (`waitUntilSaved`, up to `NEW_MASK_SAVE_WAIT_SECONDS`) and then writes by id, the copy carrying every value field of its source. Every point curve, mask and global, takes at most 16 points (`POINT_CURVE_MAX_PAIRS`; Lightroom drops a longer plain mask curve and keeps longer global ones only as an Extended companion that then wins over later plain writes), and `DevelopCurves.lua` is the global side of that law: it reads the Extended field first and writes both fields (`TONE_CURVE_CHANNELS`); curve channels are listed in `MASK_CURVE_CHANNELS` (`lightroom-tables.ts`) with their stored field names. Point Color's four actions are all `MaskValues` edits of `LocalPointColors` beside `LocalColorVariance` (`swatchAdd`, `swatchUpdate`, `swatchDelete`, `swatchesClear`): add fills the ranges Lightroom itself gives a source colour (`MaskPointColors.newSwatch`, observed equal), the four edges of every range must be ordered or Lightroom drops the whole list (a contract rule, and `MaskPointColors.requireOrderedRanges` before the gate), and deleting the last swatch or clearing removes both fields, since Lightroom drops empty arrays. No `*PointColorSwatch` call is left. Mask handlers resolve the photo through `PhotoLookup.requireOne` (an unknown photo raises `Reply.notFound`, answered as `not_found`); `MaskSelection.lua` is the one owner of mask-list readiness (`readMasks` waits up to 5 s until Develop lists at least as many masks as the saved settings hold, `holdsSavedMasks`, then refuses naming both counts; the removal of masks a failed call added waits on the same predicate, so the ids a call protects come from a complete list), the mask-on-photo check, opening and restoring the masking tool (a tool that does not open is a refusal with the previous tool restored; `selectableTool` reads the two names Lightroom is reported to give Masking, `masking` and `local_point_color` while a Point Color button is selected, as one, not yet checked live), selecting a mask by id (`withMaskSelected`, which refuses when the selection moved during its body; `keepingSelection` is the one restore of the selected mask, used by it and by invert's copy); after the redesign the selection half serves only `describe_develop_keys`' live ranges, which Lightroom answers only for a selected mask, and invert_mask's tool state (`invertMask` and `duplicateAndInvertMask` take the mask id), the mask fingerprint, removing masks a failed call added (confirmed only by a list that still holds the photo's other masks, otherwise unknown), listing a written tool, and normalising Lightroom's mask list. The schema is the only range check on a local slider write; `LrDevelopController.getRange` is read only by `describe_develop_keys`. `MaskTypes.lua` is the shared table of the Subject, Sky and Background kinds: `MASK_TYPES` in `lightroom-tables.ts` carries each kind's label and stored selector (`MaskSubType` 1, 2, and 0 with `MaskSubCategoryID` 22), the build renders it into `Contract.lua`, and `MaskTypes.component(kind, operation)` is the seed of a `Mask/Image` component without ids or digests (observed equal to Lightroom's own after the compute). `AIMaskData.lua` holds the one list of the fields Lightroom computes for the photo in such a component (the digests and their versions, `ModelVersion`, `FullMaskSize`, `Origin`, `ReferencePoint`, `WholeImageArea`, `MaskSyncID`, `ErrorReason`; a Sky copied from another photo was stored with the target's own values): the guarded read-back confirms every other field a constructed or copied component sent and never these (`AIMaskData.isComputed`), and `withoutComputedData` strips them, so a full copy sends an AI component in the form a seed has. `create_mask` and `create_mask_batch` write one entry holding that seed with the requested sliders in it (`HandlerMaskCreate.createAIMask`), and `combine_mask` appends the seed to the entry named by id (`HandlerMaskCombine.lua`; add is blend 0 value 1, subtract blend 1 value 0, intersect blend 1 value 0 inverted), all through `GuardedMaskWrite.apply` and `AIMaskCompute.run`: no Develop session, no selection, no `createNewMask` or `*CurrentMask` call, and "nothing found" is the entry's `ErrorReason`, a refusal with the mask put back and no modal alert. These are constructing writes, so they need the certification.
- Develop keys have one home, `server/src/develop-keys.ts`: `DEVELOP_KEYS` (kind, the range observed on Lightroom 16.0 or `"photo"`, precision, `photo` for keys that describe the photo rather than a look, `writtenBy` for keys another tool owns), `DEVELOP_RULES` (relations checked against stored values) and `LOCAL_KEYS`. A key enters the table only with live evidence (range, write, read-back after normalisation, rendered effect). The schemas are generated from it, and the build writes the names, flags and precisions into `Contract.lua`. `set_develop_settings` runs on the server (`develop-write.ts`: refuses keys another tool writes, rounds to precision, reads the stored values a rule needs, writes through the internal `write_develop_settings`). Lightroom normalises a write within about a second (clamps, resets some out-of-range sliders to 0, rounds); the read right after the gate only echoes the input, so every develop write is read back by `DevelopReadBack.lua` after that second and reports `adjusted`; for a photo whose write stopped, the class is the ledger's, and a read that shows the keys changed makes it unknown even when the ledger holds nothing. `describe_develop_keys` reports Lightroom's live ranges per photo; the certification run compares the static ranges and fails on a stale one without touching mask admission.
- Mask geometry (gradient position, later brush and range masks) has no SDK call, so it is written through the undocumented `MaskGroupBasedCorrections` develop setting, only via `GuardedMaskWrite.lua`: admission by certification (`MaskWriteAdmission.lua`: always on a catalog whose folder holds the live kit's `lrmcp-live-catalog.json` marker; elsewhere only when `~/.config/lightroom-mcp/mask-certification.json` names the running Lightroom build, `major.minor.revision build N` from `LrApplication.versionTable()` (`versionString()` answers only "16.0" on 16.0), and the photo's process version; a record without a build, or a Lightroom that reports none, admits nothing), a pinned per-`What` key schema checked on what the call constructs or changes (`Mask/Image` is opaque), a whole-array write, a read-back that compares the constructed entries within 1e-5 ignoring derived fields and every entry left alone exactly, and a rollback to the previous array on any mismatch. `GuardedMaskWrite.formatProblems` still reports how existing entries compare with the pinned format, through `get_mask_write_admission`'s `schema_problems`: certification reads it, admission does not. Never write that setting directly. The live kit's `certify-mask-writes.mjs` writes the certification only after its guarded-write suite passed on the throwaway catalog; after a Lightroom update, mask geometry stays refused outside that catalog until it is rerun. Widening the schema needs a live check. The argument laws of the gradient, range and brush tools are contract rules in `server/src/tool-contracts.ts`, published with each tool; `GradientGeometry.lua`, `RangeMaskGeometry.lua` and `BrushStrokes.lua` take schema-valid arguments, fill defaults and convert to stored values, and refuse only on derived or stored values (a linear gradient whose start equals its end, an update field against the stored tool's shape, a brush radius too small after feather and the dab budget, both checked on stored values in `BrushStrokes.toStoredFrame`). `plugin/spec/CertifiedGeometry_spec.lua` pins the stored geometry of the certified inputs byte for byte. Gradient handlers: `HandlerGradientMasks.lua`, conversion in `GradientGeometry.lua`. Range masks (luminance, color, depth): `HandlerRangeMasks.lua`, conversion and format in `RangeMaskGeometry.lua`. A depth range is stored as `Type -1` with a four-number `DepthRange` trapezoid (0 near, 1 far) and is refused when the read-back has no `LuminanceDepthSampleInfo`, which marks a photo without device depth; Lightroom replaces any band narrower than 0.01 with its default. A color range the plug-in constructs holds exactly one `PointModels` entry: our own two-entry write crashed Lightroom and crash-looped the catalog on reopen. Lightroom itself stores a second sample as a second entry, and such a range already on the photo is resent unchanged. Its triple is `l a b` in Lightroom's own per-photo ranking of the sampled color (lightness, green to red, blue to yellow, 0 to 1), not sRGB: the same color stores different triples in different photos (black stores `0 0.4122 0.4824` in one chart and `0 0.4872 0.5202` in another), develop edits leave it unchanged, Lightroom averages a small neighborhood when it samples, and selection follows the triple, not the x, y pin. Lua cannot compute it from RGB, so `create_range_mask` takes l, a and b verbatim and `list_masks` reads Lightroom-authored ones back (`RangeMaskGeometry.rangeOf`); `copy_sample_from` {mask_id, tool_id, optional photo_id} reuses such a range's triple, pin (mapped between the two photos' frames) and amount without knowing l, a, b, refuses any source that is not a color range with exactly one `PointModels` entry, and still writes a single entry; the busted specs hold Lightroom-authored samples as ground truth. Brush handlers: `HandlerBrushMasks.lua`, pure stroke-to-dab encoding in `BrushStrokes.lua`; a stroke's `Mask/Paint` carries `Radius`, `Flow`, `CenterWeight` (hardness) and `MaskValue` (density; 0 is an erase stroke, `MaskBlendMode` stays 0). Lightroom's Size slider is a screen size (stored `Radius` times the displayed long edge is constant, so it changes with the Develop zoom), so only `radius` is exposed. Lowering Feather shrinks the stored `Radius` and raises `CenterWeight` by a fixed curve independent of size and photo (`BrushFeather.lua`, interpolated from Lightroom-authored samples); a leading `h` dab token echoes `CenterWeight` like the `f` token echoes `Flow`, and the field alone is enough. Mask coordinates are stored in the source frame: the displayed orientation undone, before crop, straighten, lens corrections, Upright and Transform, and Lightroom renders the mask through all of them. Tools take and answer positions in the frame of the rendered preview, and `ImageFrame.lua` is the one conversion: the orientation (live check on 15.6), then the crop keys, which sit in the stored frame with `CropLeft`/`CropTop` and `CropRight`/`CropBottom` as the diagonal corners of the crop rectangle turned by `CropAngle` (closed form, live check at 8° on Orientation 1 in 16.0; an angle combined with another orientation is not yet checked live). Radial sizes and rotation and a brush `radius` (a fraction of the longer edge) go through the same pixel-space map. `set_crop` (`HandlerCrop.plan` computes, `server/src/crop.ts` writes through the `set_develop_settings` rounding and rules, then reads the keys back) plans crop keys from a frame stated before any crop with the same module. Upright, Transform and manual distortion have no inverse (measured up to about 0.05 of the frame near the edges), so the write is made with a warning; a lens profile alone moves edge points by about 0.005 and does not warn.
- `create_mask` routes `type: "people"` with `parts` and `type: "landscape"` with `categories` to `HandlerAiMasks.lua` (part tables in `AiMaskParts.lua`), separately from the original SDK type table. These People and Landscape masks also go through `GuardedMaskWrite.lua`: the SDK's `createNewMask('aiSelection', 'people'|'landscape')` makes no mask because Lightroom waits for a menu pick. Each part is a `Mask/Image` correction with `MaskSubType` 3 (all people) or 0 (landscape) and `MaskSubCategoryID` as the part (2 face skin ... 12 teeth, 13 entire person) or 50001-50008 (landscape), written without digests. Lightroom ignores `InstanceIDs` in a written mask and always masks the first person (live check on 15.6), so a single person cannot be chosen. `AIMaskCompute.run` is the only caller of `photo:updateAISettings()` and the one judgement of AI masks for every path: it does the caller's optional `GuardedMaskWrite.apply`, runs Update AI Settings in its own write gate, then polls the photo's entries until no AI component is pending, up to `AI_MASK_COMPUTE_WAIT_SECONDS` (15; on 16.0 digests are readable at the first poll). The compute is photo-wide, so the photo is what is judged: a compute gate that was never entered restores what the call wrote and refuses (the preset, which wrote nothing, answers unknown), while one that ran and raised is judged on the photo like a normal return; the wait asks `AIMaskData.uncomputed` per component; anything on the photo still pending at the limit is unknown and nothing more is written (a write during a Landscape compute froze Lightroom for a third-party client); an own entry that failed (`AIMaskData.computeState`, a non-zero `ErrorReason`) is restored through `GuardedMaskWrite.restore` and refused with the one failure text (`failureText`: it names the failed components and says "found nothing" only when each reports `ErrorReason` 1, otherwise each one's reason through `AIMaskData.errorReasonText`: 1 no result, 2 model unavailable or not loaded, 3 another failure, 4 model could not be downloaded, from static analysis; People and Landscape name the parts for `ErrorReason` 1). The call's own entries are the `CorrectionID`s that were not on the photo before, or every entry for a full copy, which replaces the masks (its process-version write is a gate and history step of its own, "Set Process Version N"); no read is compared with another by content. An entry that was already failed before the call is named in a warning and never decides; an existing AI mask whose digest changed or that became failed is named in a warning. People and Landscape (expected count = parts), Subject, Sky and Background creation, every `create_mask_batch` photo, `combine_mask` (target mode: the new components of the named entry are its own), a full `copy_develop_settings` and `apply_develop_preset`, the last two visiting each photo once however often it is named, (no write of its own, the read before the apply as its before, nothing rolled back, any outcome but done is unknown with the preset kept and the batch goes on) all ask it. A real no-result is `ErrorReason` 1 by static analysis (observed for a People part and for Subject on a featureless frame), and a digest without an error does not prove useful coverage.
- `create_mask_batch` (`HandlerMaskBatch.lua`) is one `DevelopBatch.run` whose step is `HandlerMaskCreate.createAIMask`: every photo gets the same seed entry with the requested sliders, written and judged as a single create is, with no template photo, in one Develop session that opens no photo. A photo where Lightroom found nothing fails and the batch goes on; a photo still computing at the limit is unknown and is not written to again. `AIMaskData.computeState` is the one definition of a computed AI mask (every AI component has a `MaskDigest`; a non-zero `ErrorReason` is failed), and `AIMaskData.uncomputed` the one definition of a component that is neither. A digest does not prove that Lightroom found anything useful.

- Export presets (`ExportPresets.lua`, `HandlerExport.lua`) are `.lrtemplate` files parsed as literal tables, never run. Each photo gets its own `LrExportSession` so a batch can be cancelled, so `settingsForPhoto` continues `LR_initialSequenceNumber` and writes the `naming_sequenceTotal` token as text. The session ignores `size_percentage` and truncates `size_megapixels` to a whole number (under 1 writes no file), so those become a per-photo long edge. `width`/`height` use resize type `wh` in pixels: `longEdge` ignores width and treats height as the long edge. A preset setting of the wrong type can hang the session with no error or dialog (`size_doConstrain = "yes"`, `jpeg_quality = "high"`), so `ExportPresets.invalidSetting` marks it unusable. Parallel sessions write nothing, so one `export_photos` runs at a time; the lock lapses 300 s after the last photo started, because a hung session never returns. Nothing in the SDK suppresses `AI Updates Recommended` on a photo with outdated AI settings: it blocks the call until dismissed, and Cancel reports the photo in `unknown`, since an export session is recorded before it starts, as "Export photo N (one Export history step and the exported mark)", and a session that failed after that may have left them.

Pattern verified against MIDI2LR (`rsjaffe/MIDI2LR`, see `src/plugin/Client.lua`) — same dual-port LrSocket model, ports 58763/58764 also chosen there.

## Commands

Use mise tasks from repo root:

- `mise run install` — see the task in `.mise.toml`; use `npm ci` in `server/` for locked dependency installation
- `mise run build` — `npm run build`: `server/scripts/generate-skill.mjs` rewrites the tracked `server/src/skill-content.ts` and the skill prompt text in `mcpb/manifest.json` from `skills/raw-photo-lightroom-preset/`, then `tsc` (outputs `server/dist/`), then `server/scripts/generate-contract.mjs` rewrites the tracked `plugin/LightroomMCP.lrplugin/Contract.lua` (dispatch map and tables shared with Lua) from the TypeScript contract
- `mise run test` — Jest (ESM via ts-jest)
- `mise run dev` — `tsc --watch`
- `mise run plugin:reload` — reload the installed plug-in in Lightroom Classic on macOS
- `mise run lua:lint` — `selene plugin/LightroomMCP.lrplugin`
- `mise run lua:test` — `busted` specs for the plugin
- `mise run skill:test` — Python unittest for bundled skill scripts
- `mise run live:test` — node:test unit tests for the live-test kit (`tests/e2e/live/unit/`)

Lua tooling: `mise install` provisions `lua` + `luarocks` + `selene`. `lua:test` auto-installs `busted` into `lua_modules/` (gitignored) via the `lua:deps` task. `selene` is a mise tool (`aqua:Kampfkarren/selene`), a native binary that does not run on `lua` — so unlike luacheck it is immune to Lua-version breakage. `selene.toml` configures it; `lightroom.yml` is the custom std declaring LR SDK globals; `JSON.lua` is excluded.

## CI

Workflows run on pushes and pull requests to `main`; this fork has no remote, so run the checklist below locally.

- `.github/workflows/ci.yml` — on ubuntu/macos/windows with its pinned Node version: in `server/`, `npm ci`, `npm run check`, `npm run lint`, `npm run build`, `npm run test:coverage`; from the root, the live-test kit unit tests. Its `version-consistency` job runs `node scripts/bump-version.mjs --check`.
- `.github/workflows/lua-lint.yml` — selene (via mise-action) on plugin, selene, `lightroom.yml` or `.mise.toml` changes.
- `.github/workflows/lua-test.yml` — `busted` on Ubuntu with apt Lua 5.4 (not the mise Lua), on plugin or `.busted` changes.
- `.github/workflows/skill-test.yml` — Python unittest for bundled skill scripts, on `skills/` changes.
- Type check runs `npm run check` (`tsc --noEmit` on src + `tsconfig.test.json` on tests); do not break it.
- Lint runs `npm run lint` (ESLint flat config, type-aware rules over src + tests); do not break it.

## Pre-commit checklist

- `cd server && npm run check` — type check (src + tests) must pass
- `cd server && npm run lint` — ESLint must pass
- `cd server && npm run build` — must succeed and leave tracked files unchanged unless `skills/raw-photo-lightroom-preset/` or the shared contract tables changed
- `cd server && npm run test:coverage` — Jest with the coverage thresholds CI enforces
- `mise run live:test` — live-test kit unit tests
- `node scripts/bump-version.mjs --check` — version sources agree
- `mise run lua:lint` — only if Lua changed
- `mise run lua:test` — only if Lua changed
- `mise run skill:test` — only if `skills/` changed

## Plugin install

`lightroom-mcp install-plugin` copies the bundled plug-in into the Modules folder below unless one is already there; the `stdio` server does the same at start when neither Modules nor Plugins holds a `LightroomMCP.lrplugin`. Neither replaces an installed bundle, so updating the server never updates the plug-in. To install by hand, copy `plugin/LightroomMCP.lrplugin/` to:
- macOS: `~/Library/Application Support/Adobe/Lightroom/Modules/`
- Windows: `%APPDATA%\Adobe\Lightroom\Modules\`

Bundle is pure Lua — same content ships in both `LightroomMCP-macos.lrplugin.zip` and `LightroomMCP-windows.lrplugin.zip` release artifacts. Split is for download UX, not platform code.

Click **Start Server** in Plug-in Manager. Logs at `~/Documents/LrClassicLogs/LightroomMCP.log`.

**Start-up**: Lightroom runs `LrInitPlugin` (auto-start) only when its window is first activated, not at launch: a background launch (`open -g`, automation that leaves another app in front) starts no server until Lightroom is brought to the front (`osascript -e 'tell application "Adobe Lightroom Classic" to activate'`). Verified on LrC 15.6 macOS.

**Reload behaviour**: "Reload Plug-in" creates a fresh plug-in environment (`_G`) in the same Lua VM and does **not** reliably cancel the old task's `LrFunctionContext` — the old monitor loop can keep running and hold a port (LrC 15.5.1 macOS). Before replacing the plug-in, Lightroom runs the `LrShutdownPlugin` script, `PluginShutdown.lua`, in the outgoing environment; it stops the old loop, which releases its ports through the context cleanup handler. The SDK guide runs that script only if the plug-in was loaded or reloaded through Plug-in Manager in the current session, so the first Reload after launch may skip it. Then the token file is the fallback: the new instance rewrites it, and the old loop polls it (`isSuperseded`) and exits on a foreign token. Until the old loop is gone, the new instance's binds fail with `failed to open` and recover through the reconnect path. The hook is not yet observed live on 16.0.

"Reload Plug-in" does not see a `.lua` file added to the bundle after Lightroom started: `require` fails with `Could not load toolkit script` and the plug-in is disabled. Restart Lightroom after adding a file.

## Live manual testing on macOS

`tests/e2e/live/` is the kit for live runs (README there: fixtures, tool-by-fixture verification matrix, traps). It never touches the real catalog: `openLiveSession()`, the snapshot and DB helpers and `smoke.mjs` call `requireThrowawayCatalog()`, which refuses unless the open catalog has the `lrmcp-live-catalog.json` marker written by the setup script.

- Bootstrap: `mise run build`, `mise run live:fixtures` (generates synthetic images, downloads the CC0 ARW samples into gitignored `tests/e2e/live/.fixtures/`), `node tests/e2e/live/install-bundle.mjs install`, `mise run live:setup` (File > New Catalog in a new empty folder through AX, imports the fixtures, records photo ids by fixture name in the marker), `node tests/e2e/live/smoke.mjs`. For the 200-photo batch budget: `make-batch.mjs`, then `import-batch.mjs`.
- Helpers in `tests/e2e/live/lib/`: `ax` (front-process assert and re-activate, dismiss "No X detected" and "Enable address lookup?", close Plug-in Manager), `preview` (settle protocol, region/patch deltas, IoU against an analytic shape), `catalog-db` (stored develop row and masks, flushed by switching photos), `snapshot` (copy `.lrcat` + `-wal`/`-shm` to `~/.cache/lightroom-mcp-live-snapshots/`), `plugin-bundle` (install/restore with backup outside TMPDIR, `diff -rq`), `mcp` (session against the built server).
- The throwaway catalog is rebuilt with `live:setup`, never committed. Never commit a `.lrcat`, a photo of unknown license or a depth HEIC. Depth range needs a user-supplied iPhone Portrait HEIC (`LRMCP_LIVE_DEPTH_HEIC`); depth checks skip without it.
- `mise run live:test` runs the kit's unit tests (no Lightroom); CI runs them too.
- Work from an isolated checkout. Back up the installed `LightroomMCP.lrplugin` bundle outside `$TMPDIR` before copying a candidate into `~/Library/Application Support/Adobe/Lightroom/Modules/` (`install-bundle.mjs` does it); restore the backup after testing.
- With Lightroom running, use `mise run plugin:reload` to select Lightroom MCP in Plug-in Manager and click **Reload Plug-in**. The task runs `tests/e2e/reload-plugin.applescript`; macOS must grant Accessibility access to the process running `osascript`.
- Check `lsof -nP -iTCP:58763-58764 -sTCP:LISTEN`, then call `node tests/e2e/mcp-runner.mjs tool list_collections '{"limit":1}'` from the tested checkout. A listening socket alone does not prove that requests work. Use the configured ports if they differ from the defaults.
- If reload does not answer the tool call, check Plug-in Manager. A stale `Running: true` state can remain after `Server task context cleanup`; click **Stop Server**, then **Start Server**, and retry the tool call. If the plug-in is disabled or reports a toolkit script error, close Plug-in Manager and any Save dialog, quit Lightroom normally, and reopen it. Check the sockets and tool call again. Do not force quit Lightroom or remove another process's socket.
- For collection changes, create a uniquely named temporary collection, add known photos, test member, nonmember, missing and duplicate IDs, then delete only that temporary collection. Confirm its photos remain in the catalog. Restore the original bundle and restart Lightroom when finished.
- For keyword changes, record the photo's keywords and `list_keywords` paths before testing. Use a unique temporary keyword on a known photo; verify its path and photo association after each rename, including a case-only rename. Remove the tag from the photo, then delete the empty temporary keyword in Lightroom's Keyword List and confirm the original catalog state. Restore the original bundle when finished.
- For mask changes (LrC 15.6 and 16.0), dismiss blocking modals via Accessibility before reading or creating anything: an "Enable address lookup?" modal after launching into a catalog makes menu-driven mask creation silently do nothing, and a "No subject/sky/people detected" modal blocks all Develop reads.
- `get_photo_preview` is stale right after a photo enters Develop. For preview-diff checks, set the value, wait about 3.5 s, and fetch the preview twice before and twice after.
- The develop-settings sqlite row lags until you switch photos. Flush by opening another photo, then read twice.
- Depth range masks need a photo with real device depth (iPhone Portrait HEIC); synthetic disparity files are ignored.

## Conventions

- TS strict mode on. ESM imports must include `.js` extension (NodeNext).
- New Lua handlers: add file under `plugin/LightroomMCP.lrplugin/Handler*.lua`, name it in the tool's `run: { plugin: "HandlerX.fn" }` (or in `PLUGIN_ACTIONS` for an internal action that a `run: { server }` tool calls) in `server/src/tool-contracts.ts`, run `npm run build` to regenerate `Contract.lua` (the dispatch map), declare any new LR globals in `lightroom.yml`.
- `tools/call` refuses a name with no contract, so the test-only `set_selection` action is reachable only over the raw TCP probe.
- New MCP tool: add its contract in `server/src/tool-contracts.ts` and rebuild; a Jest test fails while the tracked `Contract.lua` is stale.
- Result envelope: `server/src/tool-result.ts` derives every answer's `outcome` (`done`/`partial`/`failed`/`unknown`) from the plug-in's reply parts (`data`, `failed`, `unknown`, `not_found`, `remaining`, `problem`, `warnings`) or from the transport failure; `isError` is set exactly when the outcome is not `done`. A Lua handler returns `Reply.parts{...}` (`Reply.lua`) or a plain table, which the dispatcher sends as `data`; an error's class (`effect: "none"` for failed, otherwise unknown) comes from the call's write ledger, not from the form of the raise (see Catalog writes above); `Reply.refuse(text)` only words a refusal.
- Develop queue: contracts marked `develop: "drives"` (opens Develop) or `develop: "settings"` (writes develop settings without Develop) run one at a time in arrival order through `DevelopQueue` in the leader's call handler, so every client of the bridge shares it; a call that does not get its turn within its budget fails without sending anything, and the plug-in receives the budget left after the wait. `DevelopSession`'s single-flight check stays as the backstop for raw-socket callers.
- Time budget: a contract with `duration: "long"` gets the long server timeout, every other tool the quick default (`TIMEOUT_MS_BY_DURATION`); `createCallToolHandler` is the one place that decides it, and a server-run tool keeps all its plug-in calls within the budget it is handed. Every request carries `budget_ms`; each handler receives a `RequestContext` (`RequestContext.lua`) with `timeLeft()`, `stopping(reserveSeconds)`, cancellation and `report()` progress, so a batch stops starting items when the time left is below what one more item needs. No plug-in constant mirrors the server's timeout.
- Default ports `58763` (request) / `58764` (response). Server overrides via env vars `LIGHTROOM_MCP_REQUEST_PORT` / `LIGHTROOM_MCP_RESPONSE_PORT` (parsed in `server/src/ports.ts`); plugin overrides via Plug-in Manager fields stored in `LrPrefs` (`requestPort` / `responsePort`). Both sides must agree — change in lockstep.
